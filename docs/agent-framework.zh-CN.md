# 提案：智能体框架

[English](agent-framework.md) · **简体中文**

更新：2026-08-24

这份提案讲的是**跑 agent 的那套机器**。它们服务的闭环设计在
[`self-evolving-loop.zh-CN.md`](self-evolving-loop.zh-CN.md);这里只谈机器本身——分哪几层、每层拍了
什么决定、代价是什么、以及哪些还没有被证明可行。

它是写来被接受或被否掉的。每一条"有证据"都指向一次真实发生过的运行。

## 它是什么

五个角色，各自是一个 Python 对象。一个跑单个角色并检查其产出的 harness。一个规定谁按什么顺序跑的
脚本。外加两样它们依赖的东西:读目录改动的闸门，以及所有对外流量都走的那一个 HTTP 客户端。

```
src/agents/
  base.py        角色是什么；违反约束的角色构造不出来
  explorer.py challenger.py updater.py reviewer.py cleaner.py
  harness.py     跑一个角色：工作区、闸门、运行记录
  pipelines.py   谁按什么顺序跑
  detectors.py   cleaner 的确定性一半
  tokens.py      一次运行花了多少，按换供应商后仍可比的方式计
  memory.py      上一轮已经否掉了什么，好让下一轮不再做一遍
  schedule.py    每件事该多久跑一次；cron 只拿到一行
  __main__.py    render | list | plan | run | tokens | due | remember | rejected
```

## 八个决定，各自的代价

**1. 角色是代码，不是文档。** `base.Role` 在构造时就拒绝:持有能改文件的工具、能抓取却没被要求用共享
客户端、产出目录改动却不跑闸门。harness 读的 markdown 由对象渲染而来，所以定义与实际运行的东西不会漂。

*代价*:提示词现在写在 Python 字符串字面量里，那是比 markdown 更差的写散文的地方。*什么会推翻它*:
如果那些约束用一个扫 markdown 的 linter 表达更好，对象就没买到东西。

**2. 只在目标冲突处拆角色。** 发现与反驳要拆，因为发现方天然偏向产出;备料不拆，因为备料者没有相反
目标。

*证据*:这一对找到了第二次搜索找不到的东西。CAMD 通过了每一条机器检查(不同主机、不同名字)，最后被
否是因为 challenger 读了 `odbx.py`、发现那个数据集已经在里面。*代价*:两次运行而不是一次，而且早先
一对里有一个 agent 给出过一个必须人工纠正的错误判断。

**3. 没有东西凭 agent 的话入库。** 每个论断都落成一个不依赖 agent 的检查，而闸门读的是 diff 不是推理。

*证据*:闸门会拒绝任何触碰"新增之外"的 diff——在这条检查存在之前，一个把来源从 `rejected` 推成
`integrated` 的 diff 能**零问题通过**。*代价*:agent 做不了任何检查验证不了的事，这也正是两个角色
缺席的原因。

**4. 闸门由 harness 跑，不由 agent 跑。** 角色被要求自检;harness 照跑不误，给每次运行一个仓库外的
工作区，记录角色、任务、后端、花费与结论，只重试角色根本没跑成的那类失败，并支持从中断处恢复而不是
重跑已经成功的步骤。两个后端——可导入时用进程内的 `claude_agent_sdk`，否则用 `claude` CLI——因为那个
SDK 是 93 MB 且平台锁定的 wheel，不该进仓库的 requirements。

*证据*:下面三次运行的提案都写在仓库之外，工作树全程干净——但它们是手工驱动的，跑在这个 harness
存在之前，所以它们能证的是"工作区规则"，不是"现在强制执行它的 harness"。

*代价*:操作者与闸门之间多一层，就多一处闸门可以失败而不被看见的地方。它确实发生了:harness 调闸门时
没设 `PYTHONPATH`，闸门在 `ImportError` 上就退出了；而闸门拒绝时同样退出 1，于是"从未跑过"与"跑了说
不行"无法区分。已通过给拒绝一个专属退出码、并记录五种结果中的哪一种来修复，但这类失败是这个决定自带
的。

**5. 控制流是脚本，判断是 agent。** 不设 manager agent。`pipelines.py` 固定形状，且每一步只看得见
上一个角色留下的产物，看不见它的报告。

*证据*:§1.3 要求 challenger 自己形成判断;在此之前那靠启动它的人记得扣下报告。*代价*:固定形状无法
适应需要不同形状的那一次运行。

**6. 供应商是一道接缝，不是一个前提。** `Executor` 是唯一知道"谁在跑模型"的地方。角色、闸门、记录
与预算都按 **token** 计——那是换了厂商之后仍然可比的量;供应商的美元数与它的逐模型报告在接缝处被映射
成 `Usage`。

*代价*:中立的形状会丢掉供应商报告里放不进它的东西。*什么会推翻它*:如果第二个供应商永远不会加，
这层间接就什么都没买到。

**7. 拒绝要被记住，而记住这件事由人来做。** `memory.py` 把被否掉的候选存在
`scripts/datasets/rejected.json`，`pipelines.py` 在扫描开始时把它们读进 explorer 的任务，
于是一轮扫描不必再花钱让 challenger 把同样那四个杀第二遍。它放在**仓库里**而不是运行记录旁边，
因为一次拒绝是**一个判断**，值得作为 diff 被评审；而且只活在一台机器上的记忆，工作一挪就没了。
没有 agent 写它：人读完结果之后跑 `remember`。

*代价*:记得马虎比不记更糟——它会以一个没人能核的理由压住一个候选。所以理由是必填的，
而且交给 explorer 的那段话明确写着"拿得出证据可以再提"。*什么会推翻它*:如果拒绝理由其实很快就
过期，那么一个永不遗忘的记忆就是错的形状。

**8. 节奏是一张表，不是一条 crontab。** `schedule.py` 记着每件事该多久跑一次，cron 只拿到一行
`due --run`。节奏若活在某个人的 crontab 里，就无法在 diff 中被读到，也不会跟着仓库走。

探测器每周、`audit` 每月。**`discovery-sweep` 是手动的**——在一次无人值守的扫描跑完并被人读过之前，
不该把一个 30 万 tokens 的任务放上定时器，而这样的扫描一次都还没有；`upgrade` 根本没法排期，
因为它必须被告知是哪个来源动了。**失败的任务不会被标记为已完成**，所以它保持"到期"状态，
而不是被悄悄跳过一周。

*代价*:现在有两个地方说"什么时候发生"——这张表，以及装了那行 cron 的地方。

## 真的跑过的

| 运行 | 成本 | 产出 |
|---|---|---|
| updater 处理 core-mof 重构 | 63k tokens / 20 次工具调用 | 一份通过闸门的计划，外加**对给它的前提的纠正**——被告知全新的两个文件，其实在旧版本里就有且 md5 相同 |
| explorer | 122k tokens / 64 次工具调用 | 5 条候选、12 项"查过但排除"、每条 claim 都标了未核实 |
| challenger | 114k tokens / 41 次工具调用 | 3 条依证据否掉、2 条送专家;发现 CAMD 已在 `odbx` 里 |

一次发现扫描加一次升级，约 **30 万 tokens**。这是排期时该按的数，也是"确定性的部分必须保持确定性"
最有力的论据:探测器回答"38 个来源变没变"只要 38 个 HTTP 请求。

## 没建的，以及为什么

**两个角色。** 起草适配器、独立写 golden sample。都在等 golden sample 框架:**验证先于生产者**，所以
一个产出无人能检查的生产者不予定义。

## 真要跑起来还缺什么

- **报告的落脚处。** harness 把每次运行记在它的工作区里，但没有东西汇总它们。
- **有人去读那些账。** `python -m src.agents tokens` 能按角色、后端或日期汇总已花费的量，
  `--max-tokens` 会在会撑破上限的那一步之前停下。缺的是**上限定多少**这个决定:一次扫描加一次升级
  约 30 万 tokens，按月可负担、按周不行，而没有人说过按哪个。

## 什么会证伪这个框架

如果某次扫描产出的候选让 challenger 无从下手，那这一对就是演戏，该塌回一个角色。如果连续几轮扫描
闸门一次都没拒绝过任何东西，那它检查的是错的东西。如果 reviewer 的材料没人读，这个角色就是只有成本
没有收益。这三条**都还没有足够多的运行来判断**。
